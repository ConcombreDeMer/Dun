# Roadmap de Dun — première publication iPhone

Cette liste se lit **de haut en bas**. Chaque case décrit un résultat visible ou vérifiable, pas seulement du code à écrire. Nous passons à la suivante quand le résultat indiqué après **Terminé quand** est prouvé. Si une étape attend un accès externe, nous notons le blocage et avançons seulement sur une étape indépendante. Aucune date de publication n'est fixée avant la recette TestFlight.

Pour la tenir à jour : toute nouvelle décision modifie d'abord les règles ci-dessous, puis les étapes touchées dans le même changement. Une case cochée doit pointer vers une preuve (document, tests, PR ou recette sur build identifié). Un blocage reste écrit dans l'étape concernée ; il ne devient pas une hypothèse présentée comme un fait.

DUN-021, DUN-022 et DUN-048 apparaissent chacune en deux lots pour garder des changements vérifiables : leur tâche entière n'est terminée qu'après le second. La CI commence tôt et accueille les nouveaux tests au fil des fonctions. Les étapes « Juste après la publication » préparent le suivi sans bloquer la mise en ligne.

**État au 26 septembre 2026 :** le contrat des données locales est terminé ; la centralisation et la fiabilisation des écrans (DUN-037) restent en cours après deux revues indépendantes. Les premières corrections liées au passage à minuit ont été faites à ta demande, mais le parcours complet des dates reste à finir dans l'ordre ci-dessous. Les modifications de code en cours ne constituent pas encore un build prêt à publier.

L'[ancienne roadmap](docs/archive/ROADMAP-avant-reorganisation-2026-09-25.md) conserve l'inventaire historique, les propositions écartées et les détails techniques. **Ce document est désormais la liste de suivi et la source de vérité produit.** Les identifiants DUN sont conservés pour retrouver les travaux existants ; leur numéro n'indique pas l'ordre d'exécution.

## Décisions déjà prises pour la V1

### Matrice commerciale décidée pour la V1 publique

- **Gratuit, sur cet iPhone :** tâches datées et Box sans limite de nombre ; calendrier et historique ; Daily et verrouillage des jours passés activables ou désactivables ; mode Repos ; premier objectif ; cinq tags créables, avec trois tags maximum sur une tâche ; rappel quotidien à l'heure et aux jours choisis, week-end compris ; statistiques de la semaine ; thèmes clair/sombre/système, langue, taille du texte, calendrier en curseur et progression linéaire ; export et restauration manuels. Aucun compte Supabase ni abonnement n'est requis pour ce cœur de l'application.
- **Dun+ :** synchronisation et restauration cloud entre appareils, création de tags sans plafond produit, répétitions du rappel, statistiques mensuelles/annuelles et analyses détaillées, palettes supplémentaires, calendrier en texte et progression circulaire. RevenueCat détermine le droit à Dun+ ; le serveur doit aussi le vérifier avant une écriture cloud.
- **Après expiration de Dun+ :** les données sur l'iPhone restent disponibles. Les tags déjà créés restent actifs et modifiables ; seule une nouvelle création est refusée tant que le total atteint au moins cinq. La palette et les dispositions déjà sélectionnées restent affichées, mais le choix de nouvelles variantes Dun+ est verrouillé. Les répétitions de rappels cessent ; le rappel quotidien gratuit continue.
- **Pas dans la V1 :** routines et tâches récurrentes. Elles sont prévues pour une première mise à jour après la publication et ne doivent pas être présentées comme déjà disponibles dans l'app, le paywall ou la fiche App Store.

### Journée, objectif et Repos

- Une journée Dun se termine **à minuit**, selon le fuseau affiché par l'iPhone pour les nouvelles journées. Les journées déjà enregistrées gardent leur date. Un voyage vers l'ouest ne rouvre jamais une journée close.
- Le premier objectif est la cible choisie à l'onboarding : **1, 2, 3, 4, 7 ou 14 journées réussies**. La journée de confirmation peut compter si elle se termine à 100 %, même si des tâches ont été faites avant la confirmation. Seules les journées closes comptent ; une journée en cours à 100 % reste provisoire. Une journée vide hors Repos ou incomplète coupe la série. La première réussite reste un jalon daté ; la série actuelle peut être recalculée après une modification passée. Les statistiques utilisent exactement la même règle.
- Le Repos activé pendant une journée encore ouverte rend **toute cette journée** neutre pour l'objectif et les statistiques. « Jusqu'au 28 » inclut le 28. Si la personne annule avant minuit, la journée en cours redevient normale ; les journées déjà closes ne changent pas. On ne peut pas ajouter du Repos après coup à une journée close. Les tâches faites pendant le Repos restent consultables, mais ce jour ne compte pas dans les taux ni dans la série.
- Les comptes Supabase existants devront choisir **un nouvel objectif** lors de leur migration : l'ancien choix et l'ancien historique de Repos n'ont pas été enregistrés et ne doivent pas être inventés.

### Données et copie cloud

- SQLite sur l'iPhone devient la copie de travail pour tout le monde. Une opération n'apparaît comme réussie qu'une fois enregistrée localement. Export et restauration manuels sont gratuits. Le cloud Dun+ synchronise cette copie et permet de récupérer les données sur un autre appareil.
- À la **fin effective** du droit Dun+, la synchronisation s'arrête. La dernière copie cloud reste lisible et récupérable pendant **90 jours**, puis les données de productivité cloud sont supprimées après une nouvelle vérification du droit. Une simple annulation du renouvellement ne déclenche pas ce délai si le droit est encore actif. Une suppression explicite du compte suit son propre parcours. Aucune expiration ne supprime les données locales.

### Comment un changement devient une version iPhone

- **CI, dès les fondations :** une modification passe par une PR GitHub. GitHub Actions réinstalle les dépendances depuis le lockfile, vérifie traductions, types, lint et tests, puis affiche un résultat obligatoire avant fusion dans `master`. La suite de tests grandit avec les fonctions ; un contrôle vert sans tests métier suffisants ne valide pas la V1.
- **Environnements et données :** la CI et les builds preview utilisent des comptes, achats et données de test séparés de Dun Prod. Le candidat TestFlight construit avec le profil de production utilise la configuration de production et des comptes de recette identifiés. Les migrations Supabase passent d'abord sur une base de test, avec tests des droits ; leur application en production demande une revue, une sauvegarde et une possibilité de réparation. Aucun secret de production n'est donné à une PR.
- **Livraison :** un déclenchement contrôlé sur un commit de `master` validé crée un build EAS identifié et l'envoie à TestFlight. La recette porte sur **ce même build** ; après décision DUN-030, la mise en ligne App Store reste manuelle. En cas d'échec, on arrête la chaîne, on corrige et on produit un nouveau build traçable. La V1 ne dépend pas d'EAS Update.
